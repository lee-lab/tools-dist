# 開発記録

配布の仕組みを作るにあたっての調査結果、設計判断、実装中に踏んだ問題をまとめたものです。手順書ではありません（手順は [admin-guide.md](admin-guide.md)）。

---

## 1. 出発点

Valles を「Windows を日常的に使うが開発はしたことがない」層へ配布したい、という要求から始まりました。当時の状況は次のとおりです。

- README は `pip install -r requirements.txt` から始まっており、この層には導入できない
- `requirements.txt` に `git+https://github.com/TeamPyOgg/PyOgg.git` があり、**利用者の PC に Git for Windows が必要**だった
- `run.vbs` に特定利用者の miniconda の絶対パスがハードコードされていた
- リポジトリがプライベートのため、Release の添付ファイルの取得に認証が必要

## 2. 配布方式の選定

### 採用: uv ベースの PowerShell ワンライナー

```powershell
irm https://raw.githubusercontent.com/lee-lab/tools-dist/main/install.ps1 | iex
```

`uv` が Python 本体を用意するため、**利用者は Python の存在を意識しません**。インストールは 2〜3 分、更新は十数秒で終わります。

`irm ... | iex` の形式は、ダウンロードした文字列を実行するため PowerShell の ExecutionPolicy による制限を受けません。これが非開発者向けにこの形式が広く使われている理由です。

### 不採用: PyInstaller で単体 EXE 化

「Setup.exe をダブルクリック」が最も馴染みのある体験ですが、torch・flet・av・opencv を freeze するのは壊れやすく、サイズも 2〜3GB、依存を上げるたびにビルドの面倒を見る人が必要になります。「オフラインの現場で配る」要件が出てきたら再検討する位置づけとしました。

### 配布リポジトリを 1 つに集約した理由

GitHub Releases はタグ名で名前空間を切れるため（`valles-v1.0.0`、`othertool-v0.3.1`）、1 つのリポジトリで複数ツールを扱えます。最大の利点は**インストーラが 1 本で済む**ことで、uv の導入・Python の用意・ショートカット作成・SmartScreen 対策といった泥臭い処理を 1 箇所で保守できます。

代償として `/releases/latest` が使えなくなります（全ツール横断で最新 1 件を返すため）。そのため **`tools/<tool>.json` を配布バージョンの唯一の情報源**としました。

## 3. 依存関係の調査

### 対応 Python は 3.10〜3.12

`uv pip compile` で Windows 向けに全依存を解決して確認しました。

| Python | 結果 |
|---|---|
| 3.10 | OK（93 パッケージ） |
| 3.11 | OK（91） |
| 3.12 | OK（91） |
| 3.13 | **不可** |

3.13 が使えないのは `torch 2.3.1` に cp313 のビルドが無いためです（`Pillow 9.5.0` も同様）。README の「Python 3.10 以降」という記載は誤りだったため訂正しました。インストーラは 3.12 を固定で使います。

### PyOgg 0.7 が必須である裏付け

PyPI の PyOgg は 0.6.14a1 までで、Valles が使う `OpusEncoder` / `OpusDecoder` が**含まれていません**（`VorbisFile` のみ存在）。`requirements.txt` の「GitHub 版が必要」というコメントは正しいものでした。

しかし `git+` 依存は利用者に Git を要求してしまいます。PyOgg の `setup.py` は `PYTHON_PYOGG_PLATFORM` / `PYTHON_PYOGG_ARCHITECTURE` 環境変数でクロスビルドに対応しているため、**Linux 上から Windows 向け wheel を生成**して `wheels/` に置き、`--find-links` で供給する方式にしました（[scripts/build-pyogg-wheel.sh](../scripts/build-pyogg-wheel.sh)）。

ビルドスクリプトは、DLL 9 個の同梱と必要な API の存在を検証してから wheel を配置します。`setuptools 70` / `wheel 0.44` 以降では platform tag が付かず `-any` の wheel ができてしまうため、ビルド時のみ古いバージョンに固定しています。

### Speech2Motion に GPU は不要

`speech2motion_engine.py` は CUDA が使えれば自動で使い、無ければ CPU にフォールバックします。CPU での実測値（0.1 秒チャンクあたり、処理予算 100ms）:

| torch のスレッド数 | 平均 | 最悪 | リアルタイム係数 |
|---|---|---|---|
| 1 | 34.1 ms | 45.8 ms | 0.34 |
| 2 | 19.5 ms | 31.1 ms | 0.20 |
| 4 | 12.0 ms | 18.0 ms | 0.12 |

モデルは 4 層 LSTM（hidden 1024、29.7M パラメータ、119MB）の単方向ストリーミング推論で、そもそも GPU の得意分野ではありません。さらにメルスペクトログラムの抽出は常に CPU で実行されるため、GPU の恩恵は LSTM 部分のみです。

この結果、インストーラは **CUDA 版 torch（+2.4GB）を扱う必要がなくなりました。** Windows の PyPI wheel はそもそも CPU ビルド（160MB）なので、素直に PyPI から入れるだけで済みます。

> 補足: s2m 実行中、torch は既定で全物理コアを使います。1 スレッドでも係数 0.34 で足りるため、`torch.set_num_threads(2)` 程度に絞る方が音声キャプチャや映像デコードと CPU を取り合わずに済みます。これは配布とは別件の改善です。

## 4. 設計上の判断

### ユーザデータの保護

Valles は `settings.json`・`contents/`・s2m のモデルキャッシュを、いずれも**カレントディレクトリ相対**で保存します。これが 2 つの設計要件を生みました。

1. **ショートカットの作業ディレクトリをアプリのフォルダに設定する。** 誤ると設定が意図しない場所に書かれます
2. **更新時に退避・復元する。** アプリのフォルダはまるごと置き換わるため、マニフェストの `preserve` に列挙したものを一時退避してから展開し、あとで書き戻します

`preserve` の指定漏れは「更新のたびに設定が消える」という気づきにくい不具合になるため、テストで重点的に検証しています。

### インストール先とアンインストール

管理者権限を要求しないよう、すべて `%LOCALAPPDATA%\LeeLab\<tool>\` の下に置きます。

```
%LOCALAPPDATA%\LeeLab\valles\
├── app\          アプリ本体（更新時にまるごと置き換わる）
├── .venv\        専用の Python 環境
├── install.json  インストール状態
└── uninstall.ps1 自動生成されるアンインストーラ
```

`HKCU` のアンインストール情報を登録するため、Windows の「設定 > アプリ」から他のアプリと同じようにアンインストールできます。

### ショートカットを 2 種類作る

通常起動は `pythonw.exe`（コンソールを表示しない）ですが、それだけだとエラーが利用者から見えません。スタートメニューに `python.exe` を使う「(Diagnostic Mode)」を併設し、不具合時にエラーメッセージを読めるようにしています。

### 配布物の暗号化

一般公開前のツールを、配布物を拾った第三者が利用できないようにする措置です。tools-dist は公開リポジトリのため、暗号化しないと Releases の添付ファイルを誰でも取得できてしまいます。

- 形式は OpenSSL の `enc -aes-256-cbc -pbkdf2 -md sha256 -salt` と互換
- CI 側は `openssl`、インストーラ側は .NET の AES を使う
- マニフェストの `sha256` は**復号後**の zip のもの。復号結果をこれと照合するため、パスワード誤りを確実に検出できる（パディング検証の例外と併せて二重に検出）
- `PAYLOAD_PASSWORD` シークレットが未設定なら暗号化しない。一般公開への切り替えはシークレットの削除だけで済む

**この暗号化が守るのは「偶然拾った第三者が中身を取り出すこと」だけです。** パスワードを知る利用者による再配布は防げませんし、インストール後はソースが平文でディスク上に置かれます。アクセス制御ではありません。

CI 側とインストーラ側で実装が別れているため、片方だけ変更すると「誰も開けない配布物」が出来上がります。これを防ぐため固定の暗号化データ（`tests/fixtures/`）で相互運用を回帰テストしているほか、ワークフロー側でも暗号化直後に復号して元に戻ることを検証しています。

### 表示言語

利用者に英語母語話者が含まれるため、**利用者が目にするものはすべて英語**にしています（インストーラの表示、生成されるアンインストーラ、ショートカット名、マニフェストの説明文、リリースノート）。コード内コメントと開発者向けドキュメントは日本語です。

## 5. 実機テストで判明した問題

Windows 実機（PowerShell 5.1 / .NET Framework 4.8）で通しテストを行ったところ、**静的な構文チェックでは 1 件も検出できなかった不具合が 4 件**見つかりました。いずれも Windows 上でしか再現しません。

| 症状 | 原因 |
|---|---|
| uv の導入で即死 | astral.sh が Content-Type をテキストとして宣言しないため、`Invoke-WebRequest` の `.Content` が文字列ではなく `Byte[]` を返していた |
| Python 用意中に停止 | `$ErrorActionPreference = 'Stop'` の下では、uv が**進捗表示**を標準エラーに書いただけで `NativeCommandError` という終了エラーになる |
| 完了メッセージが文字化け | Content-Type に charset が無い JSON を既定の文字コードで復号していた |
| **更新時のみ**失敗 | `uv venv` は既存の仮想環境を上書きしない。`--clear` が必要 |

最後の 1 件は、**初回インストールだけを試していたら見逃していました。** 実運用では更新の方が回数が多いため、更新パスの検証は必須です。

### 文字コードの罠

この件は **2 段階で踏みました。** 結論だけ先に書くと、`install.ps1` は **BOM 無し・純 ASCII（コメントも英語）** が唯一の正解です。

**1 段目: BOM が無いとファイル実行で壊れる**

Windows PowerShell 5.1 は BOM の無い UTF-8 ファイルを環境の既定コードページ（日本語環境では cp932）として読みます。BOM 無しで保存した時点で、日本語のコメントが壊れて 15 件の構文エラーになりました。そこで BOM を付けました。

**2 段目: BOM があると `irm | iex` で壊れる**

ところが `Invoke-RestMethod` は、**先頭の BOM を文字列に残したまま返します。** BOM があると `<#` がブロックコメント開始として認識されず、コメント本文がすべてコードとして解釈されて、スクリプト全体が構文エラーになります。

これは **v1.0.0 を公開したあとに、実際の利用手順を実行して初めて発覚しました。** 公開したインストーラは、誰も使えない状態だったということです。

しかも、直前に行った検証では「OK」と出ていました。原因は検証コードが `System.Net.WebClient.DownloadString` を使っていたことです。**このクラスは BOM を除去しますが、`Invoke-RestMethod` は除去しません。** 実経路と 1 文字違う経路で確認したために、問題をすり抜けてしまいました。

**解決**

BOM を外せるのは、ファイルに非 ASCII バイトが 1 つも無い場合に限られます。そこで `install.ps1` のコメントをすべて英語にし、**純 ASCII・BOM 無し**にしました。これで両方の経路が成立し、文字コードの曖昧さ自体が消えます。表示はすでに英語なので、方針としても一貫します。

回帰テストとして、`install.ps1` に BOM が無いこと・非 ASCII バイトが無いこと・**`irm` が返す文字列と同じもの（BOM を除去しない復号）が解析できること**を検査しています。あわせて「BOM を付けたら壊れること」も確認し、検査自体が機能していることを担保しています。

なお、テストスクリプトと生成される `uninstall.ps1` は BOM 付き UTF-8 のままです。これらは `-File` でしか実行されず `iex` を通らないため BOM で壊れず、むしろ非 ASCII を含みうるので BOM が必要です。

### `.Count` の罠（テストで踏んだもの）

`Where-Object` の結果が 1 件だけのとき、`PSCustomObject` では PSObject のプロパティ探索が優先されて `.Count` が取れず `$null` になります。`@(...)` で配列に包んでから数える必要があります。

## 6. 検証

| 対象 | 内容 |
|---|---|
| 依存解決 | `uv pip compile` で Windows + Python 3.10 / 3.11 / 3.12 の全依存が解決可能であることを確認 |
| 実機の通し | 新規インストール → 起動環境の検証 → 更新 → アンインストールまで完走 |
| PyOgg | 実機で Opus の往復（960 サンプル → 201 バイト → PCM 復元）と Vorbis 読み込みが成功。クロスビルドした wheel の DLL が正しくロードされることを確認 |
| 暗号化 | openssl で暗号化したものを .NET で復号し、SHA256 とサイズが完全一致することを確認。誤ったパスワード・反復回数の食い違い・非暗号化ファイルはいずれも検出できる |
| 自動テスト | 単体 40 件 + 配線 22 件 = 62 件 |

自動テストは 2 本あります。

- `tests/test-install.ps1` — 個々の関数の単体テスト
- `tests/test-install-flow.ps1` — `Install-Tool` 全体の配線検証。uv・ショートカット・レジストリを差し替え、配布物は `file://` で取得するため、**実際には何もインストールせずに**全体を検証できる

どちらも副作用が無いため安全に繰り返し実行できます。

### 実測値

| 項目 | 値 |
|---|---|
| リリース zip | 572KB（`export-ignore` 導入前は 27MB 超） |
| 初回インストール | 数分 |
| 更新 | 12 秒 |
| ディスク使用量 | アプリ 1MB + 実行環境 2,159MB + uv キャッシュ 2,186MB |

uv のキャッシュは全ツール共有で、更新が 12 秒で終わるのはこれのおかげです。2 つ目のツールを入れるときも再利用されます。

## 7. 運用上の制約

### 組織シークレットが使えない

lee-lab は GitHub Free プランであり、**組織シークレットは公開リポジトリからしか参照できません。** ツール側のリポジトリはプライベートなので、`TOOLS_DIST_TOKEN` と `PAYLOAD_PASSWORD` は**ツールごとにリポジトリシークレットとして登録**する必要があります。同じトークン・同じパスワードを流用できるため、増えるのはツール追加時の 1 手だけです。

ツールが増えて登録が煩雑になった場合は、GitHub Team プランへの移行を検討する価値があります。

### トークンの有効期限

`TOOLS_DIST_TOKEN` に使う fine-grained PAT には有効期限があり、切れるとリリースワークフローが 403 で失敗します。エラーの見た目が権限設定の誤りと区別しづらいため、期限を長めに設定するか、期限日を記録しておいてください。

### 配布物の公開範囲

配布 zip はソースを含み、tools-dist は公開リポジトリです。暗号化により中身は保護されますが、**パスワードを知る利用者による再配布は防げません。** Valles は Apache-2.0 の内部ツールであり、この前提で問題ないと判断しています。
